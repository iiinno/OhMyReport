# report-design

OhMyReport の報告書作成スキル。必要な実行環境は Python 3.10 以上と Chrome・Edge・Chromium のいずれかである。

このスキルは、AIが作る報告書の見た目と構成を一つの型にそろえる。型は次の3つでできている。

- `assets/base.css` は唯一の CSS である。色、文字サイズ、余白、部品の形はすべてここで決まっている。
- `assets/catalog.html` は全部品を使った見本の報告書である。部品の HTML はここから写す。
- `scripts/lint_report.py` は報告書を実際に描画して規定違反を探す検査である。
- `scripts/archive_report.py` は完成した報告書と検査で作った PDF・画面の写しを保存用フォルダへ複製する。

この文書は2種類の内容を分けて書いている。2章「考え方」は判断の基準を定義する。定義に書いた範囲の外へ意味を広げない。3章「規定」は守るべき値と禁止事項を言い切る。規定に例外はなく、例外がある場合はその場に書いてある。

## 1. 手順

1. 読者が最も知るべきことを1文で書く。これが結論になる。
2. 資料から数値、比較、時系列、因果、条件、限界を抜き出す。数値は元の値のまま控えておく。
3. 4章の表で文書の種類を選び、章立てを決める。
4. 5章の表で、各章の材料に合う部品を選ぶ。
5. `python <このスキルのフォルダ>/scripts/new_report.py 報告書.html` で新しいファイルを作る。base.css を埋め込んだ見本の報告書が写されるので、本文を入れ替える。スクリプトが動かない環境では、`assets/catalog.html` を写し、`<link rel="stylesheet" href="base.css">` を `<style>` と base.css の全文に置き換える。base.css の中身は1文字も変えない。
6. 本文を書く。見出しは本文を書き終えてから決める（2.6）。
7. 検査を実行する。`python <このスキルのフォルダ>/scripts/lint_report.py 報告書.html --shots 写しの保存先`
8. 誤り（E）をすべて直し、誤りが0件になるまで7に戻る。
9. 保存された画面の写しを見て、6章の項目を確かめる。
10. 日本語の文章を yomiyasu スキルで推敲する。推敲のあとで、数値、固有名詞、条件、言い切りの強さが2で控えたものと同じかを照合する。
11. もう一度7を実行し、誤りが0件であることを確かめる。
12. 利用者が保存先を指定している場合は、保存用のコピーを作る。`python <このスキルのフォルダ>/scripts/archive_report.py 報告書.html --shots 写しの保存先 --dest 保存用フォルダ` を実行する。画面の写しを作っていない場合は `--shots` を省く。環境変数 `OHMYREPORT_ARCHIVE_DIR` が設定済みなら `--dest` を省ける。保存先の最新 `vN` フォルダがあればそこに保存する。同じ成果物は追加せず、変更版は短いハッシュ付きで別に残す。保存できたことを確かめてから提出する。保存先の指定がなければコピーを省く。成果物を自動で外部送信しない。

Python か Chrome（または Edge、Chromium）がない環境では7〜9と11を飛ばし、3章の規定を目で一つずつ確かめる。

検査対象は自分で生成して内容を確認した静的 HTML に限る。第三者から受け取った不審な HTML を開かない。スクリプト、イベント属性、iframe、外部 CSS は検査の前に拒否される。検査用コピーには CSP が入り、外部リソースの読み込みを制限する。この検査はブラウザのセキュリティサンドボックスの代わりにはならない。

## 2. 考え方

この章の各項は「定義」と「判定の問い」で書く。判定の問いに「はい」と答えられれば、その考え方を満たしている。

### 2.1 重要度は大きさで表す

定義: 情報の重要度は、まず面積と文字サイズ、次に余白、次に太さで表す。色と罫線はその後に使う。報告書の重要度は3段に分ける。主役は結論、最も重要な数値、最も重要な図のいずれかである。準主役には根拠、比較、各章の見出しが入り、補助には日付、条件、出典、注記が入る。

判定の問い: 画面を開いて最初に目に入る要素が、報告書で最も重要な情報と一致しているか。

### 2.2 結論を先に置く

定義: 結論とは、読者が報告書を閉じたあとに覚えていてほしい1〜2文の主張である。経緯や方法は結論の根拠であり、結論の前に置かない。

判定の問い: 冒頭の30秒で、結論と、その結論を支える最も強い数値を読み取れるか。

### 2.3 1つの章は1つの問いに答える

定義: 章とは、読者の1つの疑問（何が速いか、何が失敗したか、どこまで一般化できるか）に答えるまとまりである。2つの問いに答えている章は2つに分ける。

判定の問い: その章が答えている問いを、疑問文1つで書けるか。

### 2.4 観測と解釈を分ける

定義: 観測とは、測った値、ログ、原文、実行の記録のように、誰が確かめても同じになるものである。解釈とは、原因、推定、一般化、推奨のように、書き手の判断を含むものである。報告書のすべての主張は、どちらに当たるかを読者が見分けられなければならない。見分けるための表示は「確度」の4段階で行う（3.8）。

判定の問い: 各主張について、それが測った事実か書き手の判断かを、本文を読み返さずに言えるか。

### 2.5 密度は高くてよく、散らかりは許さない

定義: 密度とは、1画面にある意味のある要素の量である。散らかりとは、同じ重さの要素が並んで視線の入口が複数ある状態、同じ内容が別の形で繰り返される状態、意味のない色や形が混ざる状態である。情報を減らして読みやすくするのではなく、散らかりを除いて読みやすくする。空いた場所は、次の章を繰り上げるか、同じ話題の注を傍注に置いて埋める。飾りで埋めない。

判定の問い: 画面の中で、どこから読み始めればよいかが1か所に決まるか。

### 2.6 見出しは章の中身を縮めたものである

定義: 見出しは、その章が何について何を言っているかを1句か1節に縮めたものである。キャッチコピーや分類名ではない。

判定の問い: 章を読み終えた読者が見出しに戻ったとき、「この見出しはこの内容を指していた」と1文で説明できるか。説明できない見出しは書き直す。

見出しは役割に応じて次の形で書く。

| 章の役割 | 見出しの形 | 例 |
|---|---|---|
| 結果・主張 | 対象 + 何が起きたか | 成功表示と処理全体の状態が一致しない |
| 方法 | 何を + どう行ったか | 4ツールを5周、20回逐次実行した |
| 比較 | 比べる対象 + 比べる軸 | 4ツールの処理時間を5回の中央値で比べる |
| 制約 | 何が + 確認できないか | この測定では高負荷時の性能を確認できない |
| 原因 | 事象 + 条件 | 途中の回答が成功扱いされる条件 |
| 対策 | 対象 + どうするか | 成功判定は処理全体の状態を先に確認する |
| 証跡 | 何を + どう再現するか | 集計値を再生成する手順と出典 |
| 問い | 読者が実際に持つ疑問 | では、成功判定は何を見ればよいのか |

問いの形の見出しは、章の本文がその問いに直接答えるときだけ使う。

### 2.7 制作の経緯を成果物に残さない

定義: 成果物に書くのは、読者が判断に使う情報だけである。依頼の文面、受けた指示、禁止事項、使った道具、前のバージョンからの変更、デザインの意図は、見た目と構成に反映させるだけで、文章としては書かない。

判定の問い: この会話を知らない読者が読んで、不自然な一文がないか。

## 3. 規定

この章の規定には、検査が確かめる項目の番号（T1 など）を付けている。番号のない規定は検査が確かめないので、6章で目で確かめる。

### 3.1 CSS

- base.css を `<style>` に全文入れ、中身を変えない。（X2）
- base.css にない色、文字サイズ、余白を使わない。新しいクラスで値を足さない。足りない形は catalog.html の部品の組み合わせで作る。（C2、T1）
- 外部の CSS、スクリプト、フォントを読み込まない。報告書は1つの HTML ファイルで完結させる。（X1）
- `style` 属性に書いてよいのは、グラフの値（`--v`、`--r`、`--lo`、`--hi`）と表の列幅（`<col style="width: …">`）だけである。

### 3.2 文字

- 画面の文字サイズは 14、16、18、24、32、48、64px の7段階だけを使う。例外は幅の狭い画面の H1 と単位に使う 40px だけである。（T1）
- 印刷の文字サイズは base.css の `@media print` が決める 9、9.5、10.5、13、18、28、36pt だけを使う。（T1）
- 1つのブロック（冒頭、結論、各章、奥付）で使う文字サイズは5段階までにする。（T4）
- 本文の1行は42全角字まで、24px の文は34全角字までにする。（T2）
- H1、H2、H3 は2行までにする。収まらないときは文字を小さくせず、文を短くする。（T3）
- 書体は base.css の `--font-sans` だけを使う。Windows では BIZ UDPゴシックで表示される。
- 改行を `<br>` で調整しない。例外は H1 を意味の区切りで2行に分けるときだけである。
- 数値と単位、人名、製品名、モデル名の途中で行を分けない。
- ファイル名、パス、コマンド、関数名は本文でも `<code>` に入れる。`_` が本文の書体では見えにくいためである。

### 3.3 色

- 色はトークンだけを使う。（C2）
- 文字と背景のコントラスト比は4.5以上にする。24px 以上の文字と、18.67px 以上の太字は3以上にする。（C1）
- 強調色（`--accent`、`--accent-ink`）は1ブロックに1か所だけ使う。グラフ1つ、表1つは、中で何か所使っても1か所と数える。（C3）
- 見出し、小ラベル、章番号、14px 以下の文字に強調色を使わない。（C4）
- 緑、青、黄、赤は状態を表すときだけ使う。緑は確認済みと正常、青は情報、黄は注意と未確定、赤はエラーと重大な食い違いを表す。彩りのために使わない。
- グラフの主役でない棒と点は `--mark` にする。

### 3.4 面と装飾

- 影、文字の影、ぼかし、グラデーションを使わない。（S1）
- 角丸は 8px までにする。丸い点に使う 50% は 16px 以下の要素だけに使う。（S1）
- 章の背景は紙の色のままにする。色のついた面の中に、色のついた面を入れない。（S2）
- 箱で囲んだ要素を3つ以上並べない。同じ重さの項目が3つ以上あるときは、罫線で区切った一覧、表、数値の帯にする。（S3）
- 注に左端の色線を使わない。注は傍注（`.side`）か、上下の罫線で区切る注（`.note`）にする。
- 丸いピル型のラベルを使わない。状態は `.status` で、色と文言の両方で示す。

### 3.5 配置

- ページ、表、図、コードを横にはみ出させない。横スクロールを作らない。（L1）
- 大きな2列の比率は 1:1、1.618:1、2:1 の3つから選ぶ。3列以上は等分にする。（L3）
- 同格の2つを比べるときは 1:1 にし、左右の見出しの大きさと余白を同じにする。
- 1つの報告書で使う比率は3種類までにする。
- 本文の列と傍注の列は 2:1 で、base.css が決めている。傍注は、注をつける段落の直前に置く。
- 幅の狭い画面と印刷では、SVG の文字が下限を下回る図に `.only-wide` を付け、同じ内容の文字の版を `.only-narrow` で用意する。

### 3.6 表

- 1つの表は8列までにする。7列と8列の表は `<col>` で列幅を決める。（L2）
- 見出しセルは `<th>` にする。（L2）
- 数値の列には `class="num"` を付けて右に寄せる。単位は列の中でそろえる。
- 表の前に、要点を示す図か1〜2文の要約を置く。
- 識別子（ID、パス、型番）は `<span class="id">` に入れて名前の下に置く。
- 9列以上になる表は、意味のまとまり（基本情報、性能、補足など）で2つ以上の表に分ける。分けた表には同じ行の見出しを繰り返す。

### 3.7 図とグラフ

- SVG の文字は、画面で 14px 以上、印刷で 12px 以上に表示されるようにする。viewBox の幅は 880 にし、文字は 16 にする。（F1）
- 図の文字どうし、文字と矢印の先を重ねない。文字を SVG の外へはみ出させない。（F2）
- SVG には `role="img"` と、図の内容を文で書いた `aria-label` を付ける。`figure` には `figcaption` を付ける。（F3）
- グラフのすべての項目に数値を書く。点グラフには目盛りの行を付ける。（F4）
- 棒グラフの棒は 0 から始め、長さを値に比例させる。
- 凡例の箱を作らず、項目の横に直接名前を書く。
- 円グラフ、ドーナツグラフ、3D のグラフを使わない。構成比は100%の積み上げの帯で示す。
- 主役の項目だけに `is-key` を付ける。1つのグラフで `is-key` は1つだけにする。

### 3.8 確度

報告書の主張には、確度を次の4段階で付ける。確度は `.status` で示す。

| 確度 | クラス | 意味 |
|---|---|---|
| 実測 | `is-ok` | 書き手が測った、またはログで確かめた |
| 報告 | `is-info` | 利用者や第三者の報告で、書き手は確かめていない |
| 推定 | `is-warn` | 一部の観測から書き手が判断した |
| 未確認 | `is-unknown` | 確かめていない |

発見の一覧（`.findings`）の右の列と、確度の表には、必ずこの4つのどれかを書く。

### 3.9 言葉

- 「概要」「詳細」「ポイント」「考察」「まとめ」「課題」「結果」「方法」などの1語だけの見出しを使わない。（W1）
- 「〜の全貌」「徹底解説」「〜を読み解く」「Key Takeaways」などの定型句を見出しに使わない。（W1）
- 要旨（`.abstract`）は2文までにし、「何をしたか。何が分かったか。」の形で書く。「詳しく解説します」「多角的に」のような前置きを書かない。（W3）
- 「指示に従い」「〜は禁止とした」「前版から」「黄金比で配置した」のような制作の経緯を書かない。（W2）
- 見出しの上の小ラベル（`.kicker`）は、実測、検証、比較、調査、設計、結論、方法、結果、問題、制約、証跡、付録のどれかにする。英語のラベルを飾りで付けない。（W5）
- 章番号は、本文から番号で参照するときだけ付ける。（W4）
- 最後に「まとめ」や「今後の展望」の章を自動で作らない。結論は冒頭に1回だけ書く。

### 3.10 数値

- 1000 以上の数は3桁ごとにカンマで区切る（231,633）。
- 秒は `1.08 s`、文の中では `1.08秒` と書く。範囲は `0.99–4.45 s` と書く。
- 人に見せる速度は小数2桁までにする。表示のために丸めた値は、表か出典に元の値を残す。
- p95 などの統計の名前を省かない。

## 4. 文書の種類と章立て

冒頭（`.masthead`）、結論（`.conclusion`）、補助の数値（`.stats`）は全種類で使う。そのあとの章を、種類ごとに次の順で並べる。

| 種類 | 章の順 |
|---|---|
| 検証・実測 | 全体の構造の図 → 主な結果の比較 → 見つかった問題 → 制約と確度 → 再現の手順と出典 |
| 調査 | 調べた範囲と方法 → 分かったこと（問いごとに1章） → 分からなかったこと → 出典 |
| 比較・選定 | 比べる軸と条件 → 軸ごとの比較 → 推奨と、推奨が変わる条件 → 出典 |
| 障害 | 影響の範囲 → 時系列の記録 → 原因 → 対策と担当 → 再発の確認方法 |
| 設計 | 解く問題と前提 → 全体の構造の図 → 主な判断と却下した案 → 未決の事項 |

文書の題は名詞句にし、種類の語で終える（例: 検索パイプライン検証結果、更新失敗の原因調査、VPS 構成選定メモ）。

## 5. 材料と部品の対応

| 材料 | 部品（catalog.html のクラス） |
|---|---|
| 最も重要な数値 | `.metric.is-key`（冒頭の右に1つだけ） |
| 補助の数値 | `.stats` |
| 3つ以上の項目の大小 | `.bars`（横棒） |
| 少数の項目の値、範囲、基準との差 | `.dots`（点と目盛り） |
| 処理の流れ、構造 | `figure.fig` の SVG と、狭い画面用の `ol` |
| 時刻つきの出来事 | `.log` |
| 問題、発見 | `.findings`（最も重要な1件に `is-primary`） |
| 同格の2案、変更の前後 | `.split.is-equal` |
| 主と従の2つ | `.split.is-golden` か `.split.is-two` |
| 本文への補足、測り方、用語 | `.side`（傍注） |
| 注意、適用できない範囲 | `.note`（`data-kind="warn"` か `"error"`） |
| 完全なデータ | `table` |
| 生のログ | `details` の中の `pre` |
| 出典 | `.cite` と `.sources` |

## 6. 目で確かめること

検査は、意味と見た目の釣り合いを判断できない。保存された画面の写し（`*.desktop.*.png`、`*.mobile.*.png`）と PDF を開き、次を確かめる。

1. 最初の画面で、結論と主役の数値が最初に目に入るか。
2. 図、表、本文で、同じ数値が同じ値になっているか。
3. 大きな空白が残っていないか。残っていれば次の章を繰り上げる。
4. 見出しが語の途中や助詞の直後で折り返されていないか。折り返されていれば見出しを短くする。
5. PDF で、見出しだけがページの最後に残っていないか。図と説明文が別のページに分かれていないか。
6. 図の線と文字が、意図しない場所で接していないか。

## 7. 文章の推敲

日本語の文章は yomiyasu スキルが整える。このスキルは構成と見た目を決め、yomiyasu は文の書き方を決める。yomiyasu に、数値、条件、言い切りの強さ、重要度の順を変えさせない。yomiyasu がない環境では、主語を明示し、1文に1つの事柄を書き、推定は推定と書く。

## 8. 検査の規則番号

| 番号 | 確かめること |
|---|---|
| T1〜T4 | 文字サイズ、行の長さ、見出しの行数、ブロックごとの文字サイズの数 |
